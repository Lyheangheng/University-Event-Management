2. CURRENT AUTHENTICATION / IDENTITY FLOW
-------------------------------------------------------------------------------
Backend Identity Resolution Logic:
File: `apps/api/src/attendance/attendance.service.ts` -> `resolveStudent()`

The system resolves student identity in two distinct operational modes:

A. Development Mode (`NODE_ENV === 'development'`):
   1. If `x-dev-student-id` header or parameter is supplied, the backend looks up
      the student by `id` or `studentId`.
   2. If no header/parameter is supplied, the backend automatically falls back to
      the first student in the database (`prisma.student.findFirst()`).
   3. The frontend displays a "⚙️ DEV TEST SWITCHER" dropdown allowing developers/testers
      to switch identities seamlessly during local verification.

B. Production Mode (`NODE_ENV === 'production'`):
   1. The backend strictly requires a verified `lineUserId` obtained via LIFF ID token
      verification against the LINE OAuth2 API (`https://api.line.me/oauth2/v2.1/verify`).
   2. Development headers (`x-dev-student-id`) and fallbacks are hard-guarded by `isDev`
      and completely ignored/disabled in production.
   3. If `lineUserId` cannot be resolved to a linked `Student` record, the backend throws
      `UnauthorizedException('Student authentication required in production environment')`.

3. CURRENT ATTENDANCE SUBMISSION FLOW
-------------------------------------------------------------------------------
Submission Endpoint: `POST /api/attendance/sessions/:token/submit`
Frontend Component: `apps/web/src/components/attendance/StudentAttendanceForm.tsx`

What is currently sent when submitting attendance:
- `photo`: File (Multipart form data image proof)
- `feedback`: String (Optional text feedback / recommendation up to 1000 chars)
- `x-dev-student-id`: Header (Development mode identity header)

How backend associates Attendance:
1. Validates `token` against `AttendanceSession` model.
2. Calls `resolveStudent()` to determine the authoritative `Student` record.
3. Obtains `student.id` directly from the database entity.
4. Creates or updates the `Attendance` record:
   - `studentId`: Foreign key to `Student.id`
   - `eventId`: Foreign key to `Event.id`
   - `checkInTime` / `checkOutTime`: Server timestamps
   - `checkInProofUrl` / `checkOutProofUrl`: Saved storage URL
   - `status`: `INCOMPLETE` (Check-In) or `COMPLETED` (Check-Out)
   - Unique constraint enforced: `@@unique([studentId, eventId])`

Conclusion:
- The backend ALREADY knows the student's complete profile (Full Name, Student ID, Faculty, Major, Year).
- Students do NOT need to type their name, student ID, year, faculty, or major manually.

5. SECURITY FINDINGS
-------------------------------------------------------------------------------
Can a student submit attendance as another student?

- Development Mode:
  Yes. In development (`NODE_ENV === 'development'`), `x-dev-student-id` header is accepted
  to facilitate testing multiple student profiles without registering real LINE accounts.

- Production Mode:
  No. In production (`NODE_ENV === 'production'`), `resolveStudent()` disables dev headers
  and requires a valid `lineUserId` verified via LINE OAuth2 (`https://api.line.me/oauth2/v2.1/verify`).
  A student cannot forge another student's identity because the LINE ID token is cryptographically
  signed by LINE and verified server-side.
